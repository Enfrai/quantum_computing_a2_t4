# MSE802 Task 4 — Java SDK + Python Notebook

## Setup

Requires JDK 17+, Python 3.10+, NumPy, SciPy, Matplotlib, Jupyter and nbformat.

```bash
bash java-sdk/build.sh
python -m pip install -r requirements.txt
python -m unittest -v test_local_quantum_simulator.py
bash java-sdk/test.sh
jupyter notebook Task4_JavaSDK_Experiment.ipynb
```

Start Jupyter from the repository root. In the first notebook configuration cell, choose:

```python
QUANTUM_BACKEND = "local"   # default; offline, no Quokka needed
# QUANTUM_BACKEND = "quokka" # remote; requires working service
```

Set `RUN_QUANTUM = True` in section 4 to optimize using the selected backend. Run the notebook cells from the top after changing backend. For Quokka, set `os.environ["QUOKKA_URL"]` in the configuration cell to the currently working provider endpoint. The previously tested quokka1 and quokka2 ngrok endpoints were offline (ERR_NGROK_3200).

## How the local backend works

1. Java SDK emits the **same OpenQASM 2 circuit** for both backends: input X gates, recursive RY/CX gates and a final measurement.
2. `local_quantum_simulator.py` parses the generated QASM and applies X, RY and CX to a NumPy complex state vector, with qubit 0 as the least-significant bit.
3. It computes the exact Born probability of measuring 1 on the measured qubit and draws `shots` samples from a seeded binomial distribution.
4. The notebook uses sampled probabilities in the original mean absolute error objective and SciPy Nelder–Mead optimizer. It records evaluation loss and wall-clock duration.
5. The `quokka` backend instead uses Java HTTP transport and parses `result.c`. The circuit generation, objective and optimizer remain shared.

Outputs are saved to `results/quantum_local_evaluations.csv`, `results/quantum_local_loss.png`, and `results/quantum_local_time.png` (or `quantum_quokka_...` for remote runs), plus the classical baseline outputs.

## Scientific caveats

Local state-vector simulation executes on a **classical computer**, not quantum hardware or Quokka. It uses sampled measurements (not an exact-probability substitute) for training. The simulator supports only the subset of QASM generated by this Java SDK and at most 16 qubits; it is not a general-purpose QASM engine.

The 2×2 dataset contains only four images and a 75/25 split yields one test image. Quantum training vs deterministic classical inference are not equivalent workloads. Java subprocess startup is included in quantum and classical timings, while remote execution additionally includes network latency. Do not claim hardware performance or quantum advantage from this comparison.
